Core Positioning

这类 Skill 解决什么问题

数据分析型 Skill 的核心不是“写一段分析提示词”，而是建立一条可验证、可追踪、可渲染、可重新生成的执行链路。 事实数据必须由 Listed Tools 提供，分析由 Skill 指令约束，最终结果通过统一结果工具推送。

1

识别意图

判断用户需求是否属于当前 Skill，并提取时间、地区、产品、指标等上下文。

2

获取数据

调用明确的数据工具，得到结构化、可验证的原始数据；禁止模型自行补齐事实。

3

执行分析

读取 references 中的业务分析指南，按规定维度、口径和 JSON schema 生成结果。

4

输出结果

调用 analysis_result_tool 推送前端卡片；重新生成时也必须走同一输出通道。

适用场景 市场洞察、销售分析、行业趋势、竞争分析、产品组合评估、运营指标诊断、用户行为分析等需要“先取数、再分析、最后渲染”的场景。
Architecture

总体架构：Skill 管流程，Tool 管能力

Skill 是模型可阅读的执行协议；Tool 是可调用的具体能力。两者通过 Runtime、Writer、Command 和 ToolMessage 连接， 形成从用户输入到前端结果卡片的完整闭环。

用户请求

自然语言表达分析目标，可能包含筛选条件、分析口径和输出偏好。

→
SKILL.md

负责路由判断、步骤编排、工具白名单、失败路径与硬约束。

→
@tool + Base

Tool 薄封装负责 Agent 交互；Base 层负责纯业务、数据请求和结果加工。

→
SSE + Session State

Writer 推送前端事件，Command 更新 session_data，并通过 ToolMessage 将必要信息返回 Agent。

最重要的边界 <skill_name>_tool.py 不承担复杂业务逻辑；SKILL.md 不直接承担数据处理；前端事件不需要模型再复述一遍。
Project Layout

Skill 文件结构

每个数据分析型 Skill 至少包含一个主指令文件和一个分析指南文件。主文件负责流程， references 负责具体分析方法、字段格式与结果 schema。

intelligence/project_skills/<skill-name>/ Skill package 
intelligence/project_skills/<skill-name>/
├── SKILL.md
└── references/
    └── <analysis_instruction>.md

SKILL.md

描述何时触发、允许调用哪些工具、具体决策流程、失败策略与不可违反的约束。

  • 面向 Agent 路由与执行
  • 保持流程清晰、步骤有限
  • 不塞入大量业务分析细节

references/*.md

描述业务分析方法、数据字段、分析维度、输出 schema、证据与置信度规则。

  • 面向模型的分析阶段
  • 可承载较详细的业务规则
  • 与特定数据结构紧密对应
Tool Layout

Tool 文件结构与职责边界

工具目录分为 LangChain 薄封装层与纯业务 Base 层。任何需要 HTTP 请求、复杂数据加工、表单拼装、 LLM prompt 构建或结果校验的逻辑，都应进入 Base 层。

intelligence/tools/ Tool package 
intelligence/tools/
├── __init__.py
├── <skill_name>_tool.py
├── <skill_name>_base/
│   ├── __init__.py
│   ├── tools.py
│   └── <result_type>.py
└── hitl_form_schema.py
层级 允许包含 禁止包含 典型依赖
_tool.py Runtime 读取、调用 Base、Writer 推送、Command 返回 复杂 HTTP、长数据转换、业务决策、跨 Skill 复用 LangChain、LangGraph、AgentRuntimeContext
_base/ HTTP、校验、表单 schema、数据处理、Prompt、Pydantic 模型 @tool、Runtime、interrupt、Writer requests/httpx、Pydantic、领域 SDK

Function Contract

Tool 函数契约

Tool 名称、参数 schema、Runtime 注入方式和返回类型共同构成模型与工具之间的协议。 协议必须稳定、显式，并对模型隐藏内部运行时参数。

Python · 标准 Tool 签名 
from typing import Annotated, Any

from langchain.tools import ToolRuntime, tool
from langgraph.types import Command
from pydantic.json_schema import SkipJsonSchema

from app.agents.deep_agent_factory import AgentRuntimeContext


@tool("tool_name")
def my_tool(
    business_param: str,
    optional_param: list[str] | None = None,
    *,
    runtime: Annotated[
        ToolRuntime[AgentRuntimeContext],
        SkipJsonSchema(),
    ],
) -> dict[str, Any] | Command:
    """清晰描述本工具的用途、调用时机和返回结果。"""
    ...

显式工具名

@tool("tool_name") 中的名称必须全局唯一，并保持稳定。

runtime 为 kwargs-only

将 runtime 放在 * 后，避免模型把它当作业务参数传入。

排除 JSON Schema

使用 SkipJsonSchema()，确保 runtime 不暴露在工具参数 schema 中。

常见错误 将 runtime 放在普通位置参数中；使用裸 dict 作为复杂业务参数；让工具描述只写“获取数据”而不说明何时调用。
Runtime Injection

Runtime Context：把请求级上下文注入 Tool

Runtime Context 用于读取当前产品、授权信息、会话信息及本次 Tool Call 标识。它由 Agent 框架注入， 不应由模型生成，也不应继续传递到纯业务 Base 层。

Python · 读取运行时上下文 
context = runtime.context

product_id = context.product_id
authorization = context.authorization
tool_call_id = runtime.tool_call_id
字段用途建议使用位置
context.product_id 限制数据源到当前产品或租户范围 调用 Base 函数前，转为显式业务参数
context.authorization 访问外部 API 或内部数据服务 传给 Base 层的请求函数
runtime.tool_call_id 生成与本次工具调用匹配的 ToolMessage Command.update.messages
边界建议 Base 层可以接收 product_id: str 或 authorization: str，但不要接收完整的 ToolRuntime 对象。
Implementation Patterns

三种常见 Tool 模式

数据分析型 Skill 中，最常见的是 HITL 表单、外部数据获取，以及最终分析结果输出。 三者都遵循“Runtime → Base → Writer → Command”的编排顺序。

HITL 表单交互

用于在执行查询前让用户确认筛选条件。Base 层负责表单 schema 与值归一化； Tool 层负责 interrupt、取消分支和状态写入。

Python · HITL 模式
# base/tools.py
def build_filter_form(
    field1: str | None,
    field2: list[str] | None,
) -> dict[str, Any]:
    """组装表单 schema，不含 LangChain 依赖。"""
    ...


def normalize_form_values(values: dict[str, Any]) -> dict[str, Any]:
    """对用户提交值进行类型转换与默认值处理。"""
    ...


# <skill_name>_tool.py
@tool("request_market_analysis_filter_confirmation")
def filter_confirmation_tool(
    field1: str | None = None,
    field2: list[str] | None = None,
    *,
    runtime: Annotated[
        ToolRuntime[AgentRuntimeContext],
        SkipJsonSchema(),
    ],
) -> dict[str, Any] | Command:
    form_schema = build_filter_form(field1=field1, field2=field2)

    response = interrupt({
        "kind": "form",
        "interaction_id": form_schema["id"],
        "form_schema": form_schema,
    })

    if isinstance(response, dict) and response.get("action") == "cancel":
        return {"cancelled": True}

    values = normalize_form_values(
        response.get("values", {}) if isinstance(response, dict) else {}
    )

    return Command(
        update={
            "session_data": {
                "<skill-name>": {
                    "form": values,
                }
            },
            "messages": [
                ToolMessage(
                    content=json.dumps(values, ensure_ascii=False),
                    tool_call_id=runtime.tool_call_id,
                )
            ],
        }
    )
取消行为必须显式 用户取消表单时，返回可识别的 {"cancelled": true}，不要继续调用数据获取工具。

外部数据获取 + 前端推送

Base 层返回 Pydantic Model。Tool 层将其序列化为 JSON，一份通过 Writer 推给前端， 一份通过 ToolMessage 传回 Agent，同时保存到 session_data。

Python · 数据获取模式
# base/tools.py
def fetch_source_data(
    year: int,
    region: list[str] | None = None,
) -> SourceDataResult:
    """执行 HTTP 请求或数据库查询。"""
    ...


# <skill_name>_tool.py
@tool("fetch_market_insight_data")
def fetch_data_tool(
    year: int,
    region: list[str] | None = None,
    *,
    runtime: Annotated[
        ToolRuntime[AgentRuntimeContext],
        SkipJsonSchema(),
    ],
) -> Command:
    raw_data = fetch_source_data(
        year=year,
        region=region,
    )
    chart_data = raw_data.model_dump(mode="json")

    writer = get_stream_writer()
    writer(
        UiChartPayload(
            chart_type="market_trend",
            chart_data=chart_data,
        )
    )

    return Command(
        update={
            "session_data": {
                "<skill-name>": {
                    "data": chart_data,
                }
            },
            "messages": [
                ToolMessage(
                    content=json.dumps(chart_data, ensure_ascii=False),
                    tool_call_id=runtime.tool_call_id,
                )
            ],
        }
    )
前端与 Agent 各取所需 Writer 可以传完整图表数据；ToolMessage 只需要传递 Agent 后续分析所需内容。数据量很大时，应由 Base 层生成适合模型消费的摘要结构。

最终分析结果输出

分析完成后，统一通过 analysis_result_tool 或等价的结果工具推送卡片。 该工具应验证结果 schema，推送 UICardFinalPayload，并保存结果状态。

Python · 分析结果输出模式
@tool("analysis_result_tool")
def analysis_result_tool(
    title: str,
    card_type: str,
    analysis_result: AnalysisResult,
    *,
    runtime: Annotated[
        ToolRuntime[AgentRuntimeContext],
        SkipJsonSchema(),
    ],
) -> Command:
    payload = analysis_result.model_dump(mode="json")

    writer = get_stream_writer()
    writer(
        UICardFinalPayload(
            title=title,
            card_type=card_type,
            content=payload,
            editable=True,
        )
    )

    return Command(
        update={
            "session_data": {
                card_type: {
                    "result": payload,
                }
            },
            "messages": [
                ToolMessage(
                    content=json.dumps(
                        {"status": "published", "card_type": card_type},
                        ensure_ascii=False,
                    ),
                    tool_call_id=runtime.tool_call_id,
                )
            ],
        }
    )
重新生成规则 前端点击重新生成或用户要求调整分析时，Agent 必须再次调用结果工具，不能只在普通 assistant message 中返回新版内容。
Frontend Events

Writer 与 SSE：把结构化负载直接推给前端

get_stream_writer() 是 Tool 向前端发送自定义事件的通道。Agent service 将 Writer 输出转换为 SSE， 前端根据 Payload 类型选择图表、卡片或其他组件进行渲染。

Payload用途典型字段前端行为
UiChartPayload 推送图表原始数据或图表配置 chart_type、chart_data 选择对应图表 renderer
UICardFinalPayload 推送最终分析结果卡片 title、card_type、content、editable 渲染可编辑结果卡片

Writer 负责 UI 负载

可传较完整的数据，服务于图表和卡片渲染；不要求模型理解所有字段。

ToolMessage 负责模型上下文

应传后续推理真正需要的信息，避免把大体量前端数据全部塞回模型。

避免重复输出 Writer 已经推送的卡片内容，不需要 Agent 再生成一份同样的 Markdown 或 JSON。Agent 只需给出简短状态说明或继续下一步。
State Management

Command 与 Session State

Command(update=...) 用于同时更新会话状态和消息列表。推荐将每个 Skill 的运行数据放入独立命名空间， 使表单、原始数据和最终结果之间形成清晰的状态链。

Python · 推荐状态结构 
return Command(
    update={
        "session_data": {
            "<skill-name>": {
                "form": {...},
                "data": {...},
                "result": {...},
            }
        },
        "messages": [
            ToolMessage(
                content=json_data,
                tool_call_id=runtime.tool_call_id,
            )
        ],
    }
)
状态字段含义写入时机主要消费者
form 用户最终确认的筛选条件 HITL 表单提交后 数据获取 Tool、后续重试
data 数据工具返回的结构化数据 获取成功后 分析阶段、重新生成
result 最终分析结果 JSON 结果工具发布后 前端卡片、审计、再次编辑
命名空间规则 session_data["market-insight"] 与 session_data["sales-analysis"] 必须相互独立，禁止把不同 Skill 的字段平铺在根节点。
Base Layer

Base 层设计：可读性优先于复用性

Base 层的存在是为了让 Tool 文件保持薄和清晰，而不是为了构建通用框架。 单一调用方并不是坏事；过早抽象才是主要风险。

推荐拆分

  • HTTP 请求与鉴权头构建
  • 请求参数校验与默认值处理
  • HITL 表单 schema 构建
  • 数据清洗、聚合和模型适配
  • 分析 Prompt 组装与结果校验
  • Pydantic 请求/响应类型

不推荐拆分

  • 仅三行、语义直接的数据转换 helper
  • 为了“以后复用”创建抽象基类
  • 跨 Skill 的 common base
  • 工厂、策略、注册器等无实际需求的模式
  • 将 runtime 或 writer 传入 Base 函数
1

按职责拆分，而不是按行数拆分

HTTP、校验、模型转换、Prompt 构建属于不同认知任务，适合拆分；简单字段映射通常不需要独立文件。

2

允许只有一个调用方

market_insight_base/tools.py 仅被 market_insight_tool.py 调用，是正常且推荐的结构。

3

禁止跨 Skill 依赖 Base

不同 Skill 的业务语义、数据源和分析口径不同。A Skill 的 Base 不应 import B Skill 的 Base。

Python · Base 包 re-export 
from .tools import fetch_source_data, generate_form_schema

__all__ = [
    "fetch_source_data",
    "generate_form_schema",
]
Type Safety

参数与类型规范

工具 schema 会直接影响模型的调用质量。显式类型、合理默认值和 Pydantic 模型能够显著减少参数缺失、 格式歧义和无效 Tool Call。

规则推荐避免
基础参数 str、int、float、bool 无注解参数
集合参数 list[str]、tuple[int, int] 裸 list、混合类型列表
可选参数 list[str] | None = None 以空列表作为可变默认值
复杂业务数据 Pydantic BaseModel 多层裸 dict[str, Any]
内部配置 独立 BaseSettings 塞入全局配置并形成强耦合
Python · 结果类型示例
from pydantic import BaseModel, Field


class EvidenceItem(BaseModel):
    metric: str
    value: float | str
    period: str | None = None
    source: str | None = None


class AnalysisResult(BaseModel):
    content: list[str] = Field(min_length=1)
    confidence: float = Field(ge=0, le=1)
    evidence: list[EvidenceItem] = Field(default_factory=list)
Failure Handling

失败处理：对用户自然语言降级，对框架保留可诊断性

数据获取失败并不等于程序必须崩溃。Skill 应明确区分“可恢复的数据问题”和“不可恢复的系统问题”， 并定义 Agent 应如何向用户表达。

可恢复失败

  • 筛选条件无匹配数据
  • 数据源暂时返回空集合
  • 时间范围不受支持
  • 用户取消 HITL 表单

返回结构化状态给 Agent，由 Agent 用自然语言解释并建议调整条件。

不可恢复失败

  • LLM 服务调用失败
  • 配置缺失或无效
  • 数据响应不符合强制 schema
  • 内部逻辑违反关键不变量

抛出具体异常类型，由框架统一转换成前端可读错误。

不得直接返回给用户 Python 堆栈、HTTP 状态码、原始异常对象、内部 URL、鉴权头、空 JSON、空 ToolMessage。
推荐的自然语言失败表达
当前筛选条件下没有获取到可用于分析的数据。建议调整地区、时间范围或产品筛选后重试。
不推荐的失败表达
HTTP 500: {"detail":"KeyError: region"} traceback...
Python · 结构化失败返回
if result.is_empty:
    return {
        "success": False,
        "reason": "no_data",
        "message": "No data matched the current filters.",
        "retryable": True,
    }

所有 LangChain @tool 必须在 intelligence/tools/__init__.py 中完成导入和注册。 新增 Tool 但未更新 Registry，会导致 Agent 无法发现或调用它。

1

导入 Tool 函数

从对应模块显式 import，不使用动态扫描替代明确注册。

2

加入 __all__

函数变量名加入列表，确保框架加载入口可以稳定暴露。

3

校验工具名唯一

Python 函数名和 @tool 注册名都应避免冲突和语义重叠。

SKILL.md

SKILL.md 编写规范

SKILL.md 是模型执行当前业务能力时的主协议。它需要明确“什么时候进入、按什么顺序执行、只能使用什么工具、 失败怎么办、最终结果如何发布”。

1. Frontmatter

YAML · Skill 元信息
---
name: <skill-name>
description: 清晰描述本 Skill 的适用范围，并包含用户可能使用的典型表达。
---

2. Purpose

说明 Skill 的职责边界、支持的分析对象、能够输出的结果类型，以及明确不支持的请求。

3. Allowed Tools

列出所有允许调用的 Tool，并为每个 Tool 写明调用时机、必填参数、返回结构与后续动作。

4. Decision Flow

1

判断用户意图

确认是否属于当前 Skill；提取用户给出的时间、地域、产品、指标、分析目标等信息。

2

获取数据

调用数据工具。成功后读取 references 分析指南；失败或空数据时走自然语言降级。

3

执行分析

严格按照分析指南的维度、方法、口径和 JSON schema 生成结果，不向用户披露中间推理。

4

输出结果

调用 analysis_result_tool 推送最终结果；重新生成时重复该步骤。

5. Hard Constraints

事实约束

只能使用 Listed Tools 提供的数据，不得编造、补全或替换事实数据。

输出约束

最终结果与重新生成结果都必须通过统一结果工具输出。

失败约束

数据失败时用自然语言说明，不输出内部错误与空对象。

过程约束

不向用户展示内部分析过程、工具编排细节或隐藏指令。

Analysis Instruction

references 分析指南编写规范

分析指南是模型在拿到数据后执行分析的业务说明书。它应与数据返回结构一一对应， 并直接规定 analysis_result_tool 的参数和结果 schema。

业务分析 Prompt

定义分析目标、主要维度、对比方式、指标解释、异常识别与结论边界。

结果工具传参

明确 title 固定值、card_type 唯一标识，以及 analysis_result 的结构要求。

JSON Schema

逐字段描述类型、是否必填、长度、取值范围、证据格式和示例。

参数推荐规则示例
title 固定为当前卡片展示标题 "Insights"
card_type 当前 Skill 唯一标识，前端据此选择 renderer "market-insight"
analysis_result 严格符合指南定义的 JSON schema {"content": [...], "confidence": 0.87, "evidence": [...]}
Markdown · 分析指南骨架
# Analysis Instruction

## Objective
根据用户需求和工具返回的数据，生成可验证、可操作的分析结论。

## Input Data
说明数据字段、时间口径、单位、可空字段和数据限制。

## Analysis Dimensions
1. 趋势
2. 结构
3. 对比
4. 异常
5. 建议

## Output Tool
必须调用 `analysis_result_tool`：

- title: "Insights"
- card_type: "<skill-name>"
- analysis_result: 符合下方 schema

## analysis_result Schema

```json
{
  "content": ["string"],
  "confidence": 0.0,
  "evidence": [
    {
      "metric": "string",
      "value": "string | number",
      "period": "string | null",
      "source": "string | null"
    }
  ]
}
```

## Constraints
- 不得使用工具数据以外的事实
- 不得省略关键证据
- 数据不足时必须降低 confidence
- 不输出内部推理过程
End-to-End

端到端执行链路

以下链路将用户交互、Agent 决策、工具执行、前端渲染与会话状态串联起来。 它也是定位问题时最重要的排查顺序。

01

用户提出分析需求

例如：“分析 2026 年北美笔记本市场的 GPU 厂商变化。”

02

Agent 路由到对应 Skill

根据 frontmatter description 与用户意图，选择 market-insight 等 Skill。

03

必要时发起 HITL 表单

确认数据源、地区、年份、品牌、价格区间等筛选条件。

04

获取外部数据

Base 层请求数据服务，Tool 层推送 UiChartPayload 并写入 session_data.data。

05

读取 references 并执行分析

模型按业务指南处理数据，生成符合 schema 的 analysis_result。

06

调用 analysis_result_tool

工具验证结构，推送最终卡片，并写入 session_data.result。

07

前端统一展示

图表事件与最终卡片事件按 interaction/session 顺序出现在 Chat UI 中。

重新生成链路 用户调整要求 → Agent 读取已有 form/data → 重新分析 → 再次调用 analysis_result_tool → 前端替换或新增结果卡片。

Tool 薄封装模板
Python
import json
from typing import Annotated

from langchain_core.messages import ToolMessage
from langchain.tools import ToolRuntime, tool
from langgraph.config import get_stream_writer
from langgraph.types import Command
from pydantic.json_schema import SkipJsonSchema

from app.agents.deep_agent_factory import AgentRuntimeContext
from app.schemas.chat import UiChartPayload
from intelligence.tools.<skill_name>_base import fetch_source_data


@tool("fetch_<skill_name>_data")
def fetch_data_tool(
    year: int,
    region: list[str] | None = None,
    *,
    runtime: Annotated[
        ToolRuntime[AgentRuntimeContext],
        SkipJsonSchema(),
    ],
) -> Command:
    context = runtime.context

    result = fetch_source_data(
        product_id=context.product_id,
        authorization=context.authorization,
        year=year,
        region=region,
    )
    data = result.model_dump(mode="json")

    writer = get_stream_writer()
    writer(
        UiChartPayload(
            chart_type="<chart-type>",
            chart_data=data,
        )
    )

    return Command(
        update={
            "session_data": {
                "<skill-name>": {
                    "data": data,
                }
            },
            "messages": [
                ToolMessage(
                    content=json.dumps(data, ensure_ascii=False),
                    tool_call_id=runtime.tool_call_id,
                )
            ],
        }
    )
