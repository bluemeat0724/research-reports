Field guide 02 / Graph-based agents

Loop 不在一处，
而在一张图里形成。

沿着 DeepAgents 的 Python 源码，从能力装配走到模型、工具和状态更新。关键问题不是“哪里有 while”，而是：谁决定下一步，什么被写回，何时再次调用模型。

这份快照里的 middleware 顺序

“栈顺序”不等于“节点顺序”

只有实际实现 before_agent / before_model / after_model / after_agent 的 middleware 才贡献对应图节点。最简默认骨架可以是 PatchToolCalls.before_agent → model ↔ tools；profile 或可选能力会增加节点。wrap_model_call 和 wrap_tool_call 是调用包装器，在节点内部形成嵌套链。

factory.py L1814–1895

不要带着旧教程的默认值读新源码

当前通用核心栈没有 TodoListMiddleware。某些 harness profile 会再加它，例如 Codex profile。默认 authored base prompt 也不是早期统一的长提示词；最终内容由用户、profile 与运行时 middleware 共同构成。

名称命中已有项：原位替换。新名称：插到最后一个核心项之后、tail 之前。profile 的排除规则在最终栈上执行，但文件系统与子代理脚手架受保护。

这里为什么不显示“第几轮 = 第几个 step”？

LangGraph 的 step 是调度批次。before_model、model、after_model、tools 等图节点可能各占不同步；多个 Send 工具任务可以处于同一 superstep。wrapper 的重试或多次 handler 调用又可能让一次 model 节点内部出现不止一次真实模型请求。

模型 token 流和图状态流，分别看什么？

messages 模式观察模型消息片段；updates 观察节点状态更新；values 观察状态值；custom 由工具或节点主动写事件。它们服务于观察，不会取代图中的条件路由，也不能把任一流事件误认成一个完整 agent turn。

03

Loop 的开关，藏在边和包装器里

把 middleware 分成“图节点 hooks”和“节点内部 wrappers”，会比背诵一份栈顺序更接近实际执行。

Hooks：沿图走；Wrappers：在调用里嵌套
before_agent A → B
↓ 每次图执行入口
before_model A → B
↓
wrap A( B( model ) )
↓
after_model B → A
↓ tools 回边 / 结束边
after_agent B → A

A、B 指注册顺序。只列出实现该 hook 的项；不是每个 middleware 都出现在每一层。wrap_tool_call 同样构成嵌套包装链。

运行时最值得追的路由判断
  • model → tools / END / model

    显式 jump_to 优先；普通最终答复走结束路径。存在未配对工具调用时，为对应调用构造 Send；结构化输出校验分支还可能留在 model 重试。

    factory.py L1991–2042
  • tools → model / END

    工具结果已经在 state。常规返回 before_model / model；本轮路由识别出的客户端工具全部 return_direct=True 才满足该直接结束分支；人工合成结果也可能计入，不证明副作用已经执行。工具 Command 导航也是例外，不能概括成“任何工具都必定再问一次 LLM”。

    factory.py L2072–2118
  • 工具错误 → ToolMessage 或异常

    ToolNode 做工具查找、输入处理与执行。默认错误处理器仅处理 ToolInvocationError；其余异常可能传播。可以配置 handle_tool_errors，但循环没有“无条件自动修好”的保证。

    tool_node.py L922–1012tool_node.py L383–391
  • 没有下一批任务 → 图执行结束

    LangGraph 在任务为空时完成；达到 recursion_limit 则报 GraphRecursionError。中断是另一种可恢复边界，不等同于正常终止。

    main.py L2959–2989
真正的扩展问题：你要改的是“下一步去哪”，还是“本次调用怎么做”？前者考虑 hooks 的 jump_to / Command 与路由约束；后者考虑 wrap_model_call / wrap_tool_call。给系统提示加一句话，不等于改变图的执行保证。 factory.py L1814–1895
04

消息、文件和恢复，是不同的状态问题

持久化让运行可续接，但不会自动把任意外部工具变成可回滚、恰好执行一次的事务。

CONVERSATION / CHANNELS

messages 是图状态

DeepAgentState 用 DeltaChannel 存消息增量，snapshot_frequency=50；自定义 reducer 保留消息合并、删除等语义，同时降低长历史 checkpoint 的重复写入。

  • 节点返回局部更新，经 channel / reducer 合入 state
  • 工具返回 ToolMessage，用 tool_call_id 配对请求
  • 不是任意列表追加，也不是每步把全量消息重写一遍
graph.py L74–77_messages_reducer.py L31–90
FILES / BACKEND

backend 承载工具能力

默认 StateBackend 把虚拟文件放在 graph state，不等于主机磁盘。FilesystemBackend、StoreBackend、CompositeBackend 和实现 sandbox 协议的 backend 提供不同存储与执行能力。

  • 有文件接口，不代表有 shell 执行能力
  • execute 是否可用取决于 SandboxBackendProtocol
  • 文件持久化方式由 backend 和外层配置共同决定

DURABILITY / RESUME

checkpointer 保存执行进度

checkpointer + thread_id 才构成典型跨调用恢复路径。HITL 在工具执行前发出 interrupt；外部用 Command(resume=...) 提交决定，图从保存的边界继续。

  • SDK 默认不替你创建持久化 checkpointer
  • 中断恢复可能重跑包含 interrupt 的节点
  • 外部副作用仍需幂等设计与明确重试边界

总结压缩：改下一次模型输入，不是另起一个主循环

这份 DeepAgents 的 SummarizationMiddleware 实现 wrap_model_call。达到条件后会整理历史、保留相关消息，必要时将历史卸载到 backend，再将处理后的请求交给 handler。通过 _summarization_event 重建下一次有效上下文，通常保留 raw messages 主日志；必要的尾部卸载结果按消息 ID 更新。它影响上下文长度与长期任务可持续性，不能保证信息无损。

主 agent 的循环仍由 create_agent 生成的边控制。不要把摘要触发一次算成一个 tools 回合，也不要把它画成所有版本都有的 before_model 节点。

summarization.py L1487–1552
PatchToolCalls：恢复消息协议，不是补执行缺失工具

PatchToolCallsMiddleware 的 before_agent 检查历史里缺少对应 ToolMessage 的 AI tool_calls，并补充“工具未完成或未记录结果”的错误消息；非法调用还可能涉及截断或畸形参数。它修补模型消息协议，避免把悬空调用重新送入模型；不会假装原工具成功，也不会代替原工具执行副作用。

patch_tool_calls.py L11–51
task 子代理：对话隔离，不等于所有 state 隔离

标准 isolated 模式将任务描述作为子代理的新 HumanMessage；公共 state 中未被排除的字段仍可传入。子代理完成后，task 将最后非空 AI 文本，或 structured_response 的 JSON，压成一条父图 ToolMessage，并可能回传其它状态更新。

fork 模式延续父对话并重建 prompt，属于实验能力。声明式子代理、CompiledSubAgent 与远程 AsyncSubAgent 也不是同一执行路径。默认嵌套调用可继承父 runtime 的 saver / store，同时在父 tools task 独立 namespace 下保存子图进度；这不等于与父图共用一份消息历史。

subagents.py L751–843subagents.py L696–734main.py L2579–2603
HITL 批量审批：决定顺序与 tool_calls 对齐

HumanInTheLoopMiddleware 在 after_model 收集需要审批的调用。approve 保留调用，edit 保留 AIMessage 的原始调用、在工具 wrapper 中替换实际 name / args；reject 写入拒绝错误结果；respond 由人工提供工具结果而不执行工具。approve 或 edit 后仍待执行的调用，后续才进入 tools。

恢复不是把“批准”作为普通 HumanMessage 追加到对话。应使用 Command(resume=...)，并保持同一 thread_id 与可用的 checkpointer。

把容易误读的地方，留在页尾

这些区分决定调试时该去哪个文件，而不是只影响术语。

“DeepAgents 自己维护一个独立 ReAct while。”

这份 SDK 的 create_deep_agent 负责配置与委托；通用循环边在 LangChain create_agent 内构建，LangGraph 执行。定位问题先分清这三层。

graph.py L989–1011

“middleware 都是每轮按顺序跑一遍。”

有入口 hooks、每次模型调用前后 hooks，也有嵌套 wrappers。before 顺序和 after 顺序相反；有的 middleware 只有 wrapper，没有独立节点。

factory.py L1814–1895summarization.py L1487–1552

“只要配置 checkpoint，工具就是 exactly-once。”

checkpoint 持久化图状态和恢复信息，不会自动回滚数据库、邮件或 shell 副作用。重放、崩溃窗口和工具幂等性需要单独设计。

_loop.py L683–726types.py L887–911

“默认文件系统就是本地硬盘，而且能执行命令。”

默认是 StateBackend 虚拟文件。shell 能力看 sandbox 协议；但例如 LocalShellBackend 不提供进程隔离。真正的安全边界仍取决于具体 backend 与部署，不能从协议名推导。

state.py L38–119filesystem.py L3194–3240local_shell.py L26–85

“子代理一定拿不到父代理的任何状态。”

isolated 指默认不继承父消息历史；并未保证所有公共字段隔离。共享文件、传入 state、返回更新与 fork 模式都要逐项看。

subagents.py L751–843

“一个终止条件就覆盖了全部停止方式。”

自然最终答复、structured_response、return_direct、jump_to、interrupt、异常与 recursion_limit 分属不同路径。中断可恢复，错误不是正常答案。
