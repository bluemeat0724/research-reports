Pi 与 DeepSeek Harness
怎样往下走？

二者都由输入、模型、工具和边界条件推进。真正值得对比的是：谁唤醒循环，消息在哪取走，以及“结束”究竟结束哪一层。

Pi · turn≈ 模型 + 工具一轮 ≈DeepSeek · step
语义近似，不是等式。一个 DeepSeek step 可有多个 retry attempt；Pi run ≠ DeepSeek turn。

先分清边界，再比较能力

Pi 经典 core 以函数、状态与直接 hooks 组织循环；DeepSeek 默认 provider 将驱动器放进插件、服务与 session log 体系。不是靠功能或包的数量分胜负。

它们都不是永久轮询的 worker

这两条默认路线都按需启动一段异步驱动，没工作时退出。对象或宿主进程继续存在，不等于模型循环还在后台转。

      READ THE BOUNDARIES

      每一项都链接到本页固定的 commit 和对应行。

      01内核、产品层和替换点

      Pi：runAgentLoop 是低层循环；Agent 持有内存 transcript、状态和两个队列。公开 coding-agent 工厂创建 Agent 再包成 AgentSession，由后者接入资源、扩展、session 记录、重试与压缩。实验 durable 则直接把 generation/tool 实现为可持久任务，不是给同一个经典 while 外面加数据库。

      DSH：Agent 是接口，AgentLoop 是安装进 Cordis 的默认 provider，ReactLoopAgent 实现 driver。模型、工具、prompt、session 及投影都是显式服务依赖；retry 等行为可以通过独立插件挂到事件扩展点。插件组合仍然需要具体 driver，不能从“all-plugin”推断没有默认控制流。

      证据：Pi SDK 装配 ↗、Pi 实验 worker ↗、DSH AgentLoop 服务与依赖 ↗、DSH 架构与组合 ↗。

      02计数单位：turn 不能直接对齐 turn

      Pi 经典 core：一个 turn 是一次 assistant response 加它引发的工具批；一次 prompt/continue 启动的 run 可以包含多个 turn，结束事件是 agent_end。AgentSession 一次活动又可能包含多次 core run，最终有 agent_settled。

      DSH：一个 step 是一次模型请求及其工具批；一个 turn 是零个或多个 step。turn 在 claim 首批输入之前就已开始，因拦截拒绝而结束时可以没有任何 step。一次临时 driver 的 kick() 还可以连续处理多个 turn。

      因此教学上可把 Pi turn 与 DSH step 放在同一“模型＋工具一轮”的语义拍下；Pi run、Pi session 活动、DSH turn、DSH driver 没有一对一等式。DSH 一次 step 在 retry 时还能有多个 provider attempt，所以严格地说连“step＝一次 HTTP 请求”也不成立。

      证据：Pi 循环 ↗、Pi Session 外循环 ↗、DSH driver 与 turn ↗、DSH step/attempt 循环 ↗。

      03idle、入队、start/wake 与等待

      Pi：steer() 与 followUp() 只 enqueue。idle 时调用它们不会自动启动；waitForIdle() 在没有 activeRun 时可立即 resolve，即使队列仍有消息。需要调用方显式 prompt() 或合适的 continue()。已有 assistant 尾消息时，Agent.continue() 可以先 drain steering，否则 drain follow-up，重新启动；空历史不能如此继续。

      DSH：steer()＝send(next-step,true)，followup()＝send(next-turn,true)，会在 idle 时 wake；inject()＝send(next-step,false)，只入队。live driver 已忙时不另开第二个 driver，现有流程会到检查点取输入。maintenance 或已 abort 的活动收到 waking input 时可 latch wake，等旧活动收敛再开新 driver；disposed 不重启。whenIdle() 会追踪 activityDone 的更替，而不是只等捕获到的旧 promise。

      注意 DSH status 在 maintenance 中也显示 idle；这不意味着没有需等待的工作。idle、inbox 为空、无维护活动、driver 结束是不同条件。

      证据：Pi enqueue ↗、Pi idle/prompt/continue ↗、DSH send/wake/maintenance ↗、DSH status ↗。

      04队列结构、批量策略和消费检查点

      Pi：独立 steering 与 follow-up FIFO，默认各自 one-at-a-time，可改 all。run 开始检查 steering；完整 turn 结束后先检查 steering；只有没有工具续转和 steering 续转时才取 follow-up。在已决定开始下一 turn 后，会运行 prepareNextTurn；若先前未选到任何 pending messages，再补查一次 steering。已选一条 steering 或 follow-up 时不会补取，不保证后来到达的 steering 越过已选的 follow-up。prepareRequest 后不再补查。

      DSH：inbox 是 next-step、next-turn 两个日志投影。每次 preStep 的 claim 取走全部 next-step；只有 turn 第一轮 target 为 next-turn 时，额外取一条 next-turn，并放在 next-step 输入之后。claim 在 prompt assembly 和 agent/pre-step 之前；其间新到达的消息留待下一 step，retry 也不重新 claim。当前工具批中不会插入一次 claim。

      DSH 所谓 durable claim 是已记录的 inbox splice，不等于输入已通过 pre-step 或已送到模型；磁盘抗崩溃保证还取决于 persistence backend 与 flush。两者的 API 名字相似，但默认 drain 数量与 wake 行为不同。

      证据：Pi FIFO 与模式 ↗、Pi 精确检查点 ↗、DSH claim ↗、DSH preStep ↗、DSH splice 记录 ↗。

      05输入接纳与模型上下文

      Pi：core 的 prepareRequest、transformContext、convertToLlm 提供分层准备与转换。AgentSession 先做 input/slash/模板处理，再把 canonical session projection 装入请求；raw history 与请求投影不应混淆。

      DSH：claim 只是取走候选输入。agent/pre-step 可以改写或 reject；reject 会记 turn/end: blocked 并停止本 driver，这批已 claim 输入不会自动退回 inbox。稍后新入队的输入仍可保留。进入 step 后，agent/request 与 provider prepareCall 先解析实际路由，再记录 system/user 消息；deriveMessages() 从 session log 生成并冻结请求。每个 attempt 刷新 runtime context，原输入只在首次 attempt 接纳。

      页面不应把两者都画成“先从队列弹出就立刻调用模型”。也不能把 DSH 的 pre-step reject 等同于取消当前模型请求，或等同于 Pi finishTurn({action:'end'})。

      证据：Pi request hooks ↗、Pi Session 接线 ↗、DSH preStep/拒绝 ↗、DSH 请求接纳 ↗、DSH 从日志构造请求 ↗。

      06工具并发、顺序与“结束”提示

      Pi：默认 parallel；只要全局 sequential，或本批任何已调用工具标记 sequential，整批改串行。parallel 中 start/验证/before hook 按源码调用顺序预检完，再用 Promise.all 启动允许的执行；执行结束事件可以按完成先后出现，但 toolResult transcript 消息按模型原始顺序输出。terminate:true 必须非空批次每个 finalized result 都为真，才抑制工具结果触发的自然续转；不取消兄弟工具，也不压过后续队列或明确 continuation。

      DSH：工具只有 isConcurrencySafe(args) === true 才可并行，其余（包括未声明）exclusive。并行使用 bounded rolling pool，默认上限 10；exclusive 是局部 barrier，前面 drain 后独占执行，后面的 parallel 仍可并行。后续调用开始前重新分类；body dispatch 可重叠，pre-execute 与结果 finalize/commit 保持模型顺序。concludesTurn 是任意一个 committed result 为真即成立（OR），但整批兄弟仍完成；新 next-step 输入及 stopping hook 仍可能延长 turn。

      这不是“二者都有 parallel 所以相同”：Pi 的整批模式选择、无此批内 pool cap 的 Promise.all，与 DSH 的逐调用 opt-in、rolling pool、局部 barrier 是不同策略。不能凭此推出真实任务谁更快。输出截断也不同：Pi stopReason:length 为该 response 的工具调用生成错误结果而不执行，再允许模型修复；DSH max-tokens 在工具分派前返回结束原因，后续 step 不把这个 turn 原因降级为普通 completed。

      证据：Pi 模式选择与执行 ↗、Pi all-terminate ↗、DSH pool/barrier/ordered commit ↗、DSH opt-in 分类 ↗、DSH 默认上限 ↗。

      07取消：signal、队列和未执行工具

      Pi：Agent.abort() 只 abort active controller，不自动清空 steering/follow-up，但不能据此断言任何取消时序中队列都原样保留：工具阶段 abort 后，后续 finishTurn/poll 仍可能取走输入。工具与 provider 需要合作；串行批在一个调用 finalize 后检查 abort，parallel 等已启动的 promise，非合作工具可延迟 idle。取消不是回滚。若 provider 产生 aborted assistant，core 调 finishTurn 但忽略其 continuation 决定，然后硬退出且不再新 poll 队列；意外 throw 还有 Agent failure adapter 路线。

      DSH：cancel(cause) 默认先 clear inbox，再 abort；keepInbox:true 可保留队列，但保留本身不保证取消结束后自动 wake。工具 scheduler 停止补充新调用，等待已启动调用收敛，按序提交结果，并给未 dispatch 的模型工具调用补合成 aborted 结果。之后关闭 step 与 aborted turn。取消后新收到的 waking message 会转 next-turn 并 latch，避免加入已 aborted 活动。

      两边都不能强行终止任意 JS promise，也不自动撤销已经发生的外部副作用。模拟应声明“provider/工具响应 signal”这一 fixture 条件。

      证据：Pi abort/idle ↗、Pi 工具取消检查 ↗、Pi error/aborted 出口 ↗、DSH cancel 与重唤醒 ↗、DSH 工具取消补齐 ↗。

      08重试与压缩属于哪层

      Pi：经典低层 run 遇 assistant error/aborted 会退出；coding-agent 的 AgentSession 外循环才负责识别 transient error、预算/可取消 backoff、再 agent.continue()。失败 raw history 可保留，同时通过 context edit 从模型投影移除。overflow/压缩恢复与普通 retry 是不同路径；压缩也可能在请求或 turn 间发生，不能一概画在 agent_end 后。provider HTTP 层还可以另有 transport retry。

      DSH：默认 loop 为 stream 协议化的 error/aborted finish 提供 agent/request-error waterfall；llm-retry 插件按 provider retryPolicy 决定 budget/backoff，先记录 llm/retry，可取消等待后记录 llm/retry-started，返回 retry。loop 在同一 step 的内部 while 重做 request preparation/attempt；不重复 preStep、assembly 或 claim，不重复追加本批原 user 消息。失败 attempt 记录为 assistant/attempt，不是正常模型历史里的 assistant answer。不是所有任意 throw 都经过此 waterfall：stream 创建或迭代直接抛出的异常可能结算后直接退出。没有相应插件或返回 retry 的 handler 时，不能声称 core 自动重试。compaction 同样由外围能力接入。

      可比的是“错误如何成为下一次 attempt”，不是把两条路径写成同一个 retry 节点。一次高层 Pi prompt 可能出现两次 agent_end、一次 agent_settled；DSH 同 step 内重试通常尚未出现 step/end。

      证据：Pi Session 恢复循环 ↗、Pi transient retry ↗、DSH retry seam ↗、DSH retry 插件 ↗。

      09日志、持久化与崩溃恢复

      Pi 经典 core/Session：core 的数组与队列本身是进程内状态；AgentSession/SessionManager 接入会话持久记录与重建模型投影。保存 transcript 不等于在崩溃点恢复未完成 JS 调用。

      Pi 实验 durable：generation/tool 是有 checkpoint phase 的任务；scheduler 恢复遗留 running task，再显式 resume/submit/wait 推进。ToolTask 先存执行 intent；恢复重放要求存储和当前工具都标 safe，默认 unsafe 时记录 interrupted，不自动重做可能已有副作用的调用。safe 也不是 exactly-once 证明。SQLite/JSONL/Memory backend 的耐久性不同，库内 single owner 与 worker 外层目录锁要分开。

      DSH：Session log 与 inbox projection 是默认 driver 的基础；是否跨进程持久取决于挂载的 SessionPersistence。resume 先获取 write ownership，再修补中断尾部的缺失 tool result、step/end、turn/end；这是日志与会话恢复，不是继续保存过的 JS 栈或任意工具 phase。handle append 的公共约定是有序且本 backend 可见，flush 才是承诺抗崩溃的屏障；close 会 drain 并释放 ownership。

      不要写“Pi 不支持持久化、DSH 支持”或反向写“有 durable 所以 Pi 默认都是 durable”。必须说明比较的具体路线。

      证据：Pi Session 记录 ↗、Pi durable 工具重放 ↗、Pi scheduler 恢复 ↗、Pi 实验发布范围 ↗、DSH resume 修复 ↗、DSH persistence handle 保证 ↗。

      10扩展控制流与事件背压

      Pi core：before/afterToolCall、prepareRequest、prepareNextTurn、finishTurn 是直接注入的控制 hook。finishTurn 可 end 或 continue。Agent.subscribe listener promise 按注册顺序 await，可让 agent_end 已发但 run 尚未 idle。AgentSession.subscribe 公开 emit 并不 await listener promise。公开扩展 BoundaryResult 只有 entries/continue，不能把 core {action:'end'} 当作 pi.on('turn_end') 的返回协议。

      DSH：typed events 分清三种模式：emit 是非阻断通知且单 listener 异常被隔离；serial 等待按序链；waterfall 是带 next 的 around middleware，必须主动 delegate 才进入下游。pre-step、request、request-error 和 tools 管线可拦截；turn-stopping 是 awaited serial，可注入更多 next-step。agent-scoped 注册随 scope dispose 撤销。

      两者都有扩展性，但控制点的时机、返回值与错误语义不同。“有事件监听”并不等于“可 veto”，“async handler”也不自动代表 runtime 等它。

      证据：Pi Agent listeners ↗、Pi Session emit ↗、Pi public BoundaryResult ↗、DSH dispatch 三种模式 ↗、DSH stopping checkpoint ↗。

      11对外集成与生命周期所有权

      Pi：可直接嵌入 Agent/core 或 createAgentSession，也可用 stdin/stdout JSONL RPC 连接 coding-agent。RPC prompt success/started 表示 preflight 通过并接纳启动，不代表回答结束；handled 甚至可能没有模型 run。extension/UI 是另外的宿主接线。

      DSH：可替换的 in-process agent service 是体系内部扩展面；受支持的 Node 应用启动通过 profile 与 ordered patches，TypeScript/Python SDK 启动对应的 dsh profile/JSON-RPC 宿主。AgentLoop create/resume 管理 session write handle、scope、registry 与异步创建监听；dispose 先 cancel＋whenIdle，再 scope dispose、storage close、撤出 registry。这不是单个 await generate 的 ownership 约定。

      集成决策应先问：需要一个可嵌入循环、完整本地 coding-agent、或可组合的应用宿主？不应把内部 service 示例当作另一个受支持的公开启动器。

      证据：Pi SDK ↗、Pi RPC prompt ↗、DSH profile 启动约定 ↗、DSH 有序 teardown ↗。

      12进程、插件隔离与多租户边界

      Pi：经典 Agent ID/Session ID 和 cwd 是应用状态，不自动构成 tenant ACL。实验 durable 支持 per-conversation environment、task ownership 与多个 conversation，但源码中的 eligible-task reservation 并不是按 tenant quota/fair-share 的调度器。NodeExecutionEnv 接受绝对路径，cwd 本身不是安全沙箱；实验服务明确还需 authenticated per-client projection/workspace authorization/plugin policy。

      DSH：agent scope、preset/realm 解决注册、服务选择和生命周期归属；工具并发上限是每 step 执行策略，不等于跨租户公平配额。仓库确有外围认证、session controller、sandbox/approval 能力，不能说“没有安全”。但 native plugin 同进程服务隔离、session write ownership、process sandbox、authenticated caller→session 授权是不同问题；不能凭插件树或单 writer lock 宣称它已构成通用 SaaS 多租户隔离。sandbox-local 自身共享 host kernel/filesystem，强环境隔离需独立 container/remote 等能力。

      面向多租户平台，两边都要单独设计并核验：身份与会话授权、密钥边界、执行环境隔离、租户配额/公平性、持久写入 ownership、审计与崩溃副作用策略。这个结论是部署边界分析，不是对整个仓库做“绝无此功能”的穷尽断言。

      证据：Pi durable Node 路径 ↗、Pi 实验服务范围 ↗、Pi durable scheduler ↗、DSH scope 路由 ↗、DSH pool cap ↗、DSH process sandbox 边界 ↗、DSH session controller 的外围职责 ↗。

      “持久化”不等于恢复任意执行现场

      Pi 经典 core、AgentSession 与实验 durable 是不同路线。DeepSeek 的 session log、inbox 投影、存储 flush 和 resume 修复也各有边界。不能从保存了历史，直接推导任意工具可 exactly-once 重跑。

      “插件化”也不等于多租户安全边界

      身份与会话授权、执行隔离、密钥、配额与副作用恢复，需要单独核验。两个循环的结构比较，不构成对整个项目的性能排名、安全认证或生产部署承诺。
